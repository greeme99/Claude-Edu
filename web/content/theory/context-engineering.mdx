## 1. 프롬프트만으로는 끝났어요

### 프롬프트를 갈아도 결과가 나아지지 않는 지점이 와요

<Term id="T-PE" />은 AI 활용의 출발점이에요. LLM에게 지시를 설계해 원하는 행동을 끌어내는 실무 기술이죠. 모델의 가중치를 건드리지 않고, 입력 텍스트의 구조·예시·역할·출력 형식만으로 행동을 조정하는 거예요.

GPT-3 논문(Brown 등, 2020)이 보여준 것처럼, 충분히 큰 모델은 파인튜닝 없이 프롬프트 안의 몇몇 시연만으로 다양한 과제를 풀어요. 이 발견이 현대 프롬프팅의 출발점이었고, 가장 싸고 빠른 성능 레버였어요.

이 기술의 도구 상자는 풍부해요. <Term id="T-ZERO" />, <Term id="T-FEW" />, <Term id="T-COT" />, <Term id="T-STRUCT" />까지. 방법론은 성숙했어요.

그런데 이 기술에는 천장이 있어요. 영어로 바꿔보고, 시스템 프롬프트를 구조화하고, Few-shot 예시를 5개, 10개까지 넣어봐도 어느 순간 결과가 더 이상 좋아지지 않는 지점이 와요.

| 시도 | 효과 | 한계 |
|---|---|---|
| 영어 프롬프트 | 일부 작업에서 개선 | 한국어 결과물이 필요하면 원점 |
| 시스템 프롬프트 구조화 | 처음 3턴은 효과적 | 이후 모델이 지시를 은근히 무시 |
| Few-shot 예시 추가 | 품질 향상 | 컨텍스트 윈도우를 점유해 작업 공간 축소 |

세 가지 시도 모두 "프롬프트를 더 잘 쓰기"의 범주에 있었고, 전부 <Term id="T-CTXWIN" />라는 유한한 공간 안에서의 트레이드오프에 부딪혔어요.

프롬프트를 개선하면 프롬프트가 차지하는 토큰이 늘어나고, 그만큼 다른 정보가 밀려나요. 이것은 제로섬이에요. 프롬프트를 최적화하는 행위 자체가 컨텍스트 전체의 균형을 깨뜨리고 있었던 거예요.

### 0.25%의 의미 — 면접장의 첫 마디 인사

이 숫자를 직시해야 해요. 컨텍스트 윈도우가 200K 토큰이라고 할 때, 30분 동안 공들여 쓴 프롬프트가 500 토큰이라면 그것은 전체 윈도우의 **0.25%**예요. 윈도우가 1M 토큰으로 커져도 원리는 같아요.

나머지 99.75%는 무엇으로 채워질까요?

```
구성요소                      비중      누가 넣는가
시스템 프롬프트                  5%      하네스가 자동 삽입
프로젝트 설정                    2%      하네스가 자동 로드
도구 정의                        3%      하네스가 자동 노출
이전 대화 기록                   5%      턴마다 자동 누적
도구 출력 (파일 내용, 검색 결과) 80%+     도구 실행 결과
내 프롬프트                   0.25%      사람이 직접 작성
```

프롬프트 0.25%와 도구 출력 80%+. **300배 이상의 격차**예요.

비유하면 이렇게 돼요. 면접을 본다고 가정해보세요. 면접관 앞에 이력서, 포트폴리오, 추천서, 자격증, 이전 회사 평가서가 놓여 있어요. 프롬프트는 면접장에 들어서면서 하는 첫 마디 인사예요. 그 인사를 아무리 완벽하게 해도, 포트폴리오가 엉망이면 면접에서 떨어져요.

<Callout type="key" title="여기까지의 핵심">
프롬프트는 컨텍스트 윈도우의 0.25%에 불과해요. 나머지 99.75%를 무시한 채 0.25%만 다듬는 것은, 면접 인사만 연습하면서 포트폴리오를 방치하는 것과 같아요.
</Callout>

## 2. 대화가 길어지면 AI가 바보가 되는 이유

### Lost-in-Middle

프롬프트 엔지니어링으로 해결할 수 없는 문제가 있어요. 대화가 길어지면 초반 지시가 사라지는 현상이에요.

실전 시나리오를 볼게요. B2B SaaS 마케팅 콘텐츠를 만드는 상황이에요. 첫 턴에 "전문적이되 딱딱하지 않은 톤, 추상적 수식어 금지, 구체적 수치 필수"라고 지시했어요. 1~3턴까지는 훌륭해요. 4~5턴부터 금지한 표현이 하나씩 끼어들고, 6턴 이후에는 명시적으로 금지한 표현이 버젓이 나와요.

왜 이런 일이 벌어질까요? 트랜스포머의 어텐션 메커니즘이 **U자형 분포**를 보이기 때문이에요. 앞부분(시스템 프롬프트 근처)과 뒷부분(최근 대화)에는 높은 주의를 기울이지만, 가운데(초반 대화 기록)에는 낮은 주의를 기울여요. 이것이 <Term id="T-LIM" /> 현상이에요.

교실에 비유하면 이해가 빨라요. 선생님이 수업 시작할 때 한 말과 방금 한 말은 잘 기억하지만, 20분 전에 한 말은 기억이 흐릿해지는 것과 같아요.

2026년의 모델들은 컨텍스트 윈도우가 1M 토큰까지 늘어났고 어텐션 메커니즘도 개선됐어요. 하지만 근본 원리는 변하지 않았어요. 대화가 충분히 길어지면 초반 지시가 가운데로 밀려나면서 영향력이 줄어들어요. **윈도우가 커졌으니 발생 시점이 늦춰졌을 뿐이에요.**

이 문제에 대한 나쁜 대응은 "아까 한 거 잊지 마"라고 다시 말하는 것이에요. 프롬프트로 프롬프트 문제를 해결하려는 시도인 거예요. 일시적으로 듣지만 몇 턴 뒤에 또 반복돼요.

좋은 대응은 세 가지예요.

1. **시스템 프롬프트에 핵심 규칙을 넣어요.** 컨텍스트의 맨 앞에 위치하므로 어텐션이 항상 높아요.
2. **세션을 짧게 끊고** 핵심 규칙과 함께 새 세션을 시작해요.
3. **<Term id="T-CLAUDEMD" /> 같은 프로젝트 설정 파일을 활용해요.** 매 세션 시작 시 자동으로 로드되므로 밀릴 수가 없어요.

프롬프트는 대화 기록 안에 들어가서 뒤로 밀려요. CLAUDE.md는 시스템 수준에서 매 턴마다 로드돼요. 이것은 프롬프트를 잘 쓰는 기술이 아니라 **컨텍스트를 관리하는 기술**이에요. 자세한 것은 <LessonLink id="TH-04" />에서 다뤄요.

### 4가지 실패 모드

Chroma Research(2025)가 18개 최신 모델을 벤치마크한 결과, 컨텍스트가 논리적으로 일관될수록 오히려 성능이 나빠졌어요. 200K 토큰 모델이 50K 토큰 지점에서 이미 불균일한 성능 붕괴를 보였어요. 윈도우의 25%만 채웠는데도요.

**불균일**이 핵심이에요. 균일하게 나빠지면 예측이라도 가능하지만, 어떤 질문에는 완벽히 답하고 바로 다음 질문에는 완전히 실패하는 패턴이에요.

| 실패 모드 | 원인 | 대응 |
|---|---|---|
| Context Poisoning (오염) | 환각이 컨텍스트에 들어가 자기강화 루프 형성 | 검증 게이트, 메모리 쓰기 승인 |
| Context Distraction (산만) | 무관한 정보가 핵심 신호를 희석 | 필요한 것만 선택, 요약 기반 검색 |
| Context Confusion (혼란) | 도구와 규칙이 너무 많아 결정 불가 | 도구·규칙 축소, 격리 |
| Context Clash (충돌) | 초반 지시와 후반 지시가 정면 충돌 | 주기적 재지시, 요약 재주입 |

컨텍스트 문제를 인식하면, 그동안 "AI가 멍청해서"라고 생각했던 현상들이 전부 설명돼요. "같은 프롬프트인데 어제는 됐고 오늘은 안 된다"도 마찬가지예요. 프롬프트는 동일하지만 어제는 새 세션의 첫 턴이었고 오늘은 5턴이 쌓인 세션이에요. **프롬프트가 전체의 0.25%라면, 나머지 99.75%가 다른데 같은 결과를 기대하는 것이 오히려 이상한 거예요.**

## 3. 컨텍스트 엔지니어링 — 정보 건축의 시대

2025년 6월 셋째 주, 실무에서 벽에 부딪힌 사람들이 거의 동시에 같은 결론에 도달했어요. Shopify CEO Tobi Lutke가 이름을 붙였고, LangChain의 Harrison Chase가 동조했고, Andrej Karpathy가 정의를 확립했어요.

<Callout type="quote" title="Karpathy의 정의">
Context engineering is the delicate art and science of filling the context window with just the right information for the next step.

다 넣는 게 아니라 **딱 맞는 것만**. 전체가 아니라 **바로 다음 한 단계**를 위해.
</Callout>

이것은 트렌드가 아니었어요. CEO, 프레임워크 제작자, 연구자, 비평가가 서로 다른 위치에서 같은 벽을 보고 같은 이름을 붙인 거예요.

<Term id="T-CE" />은 윈도우에 무엇이 어떤 형식으로 언제 들어가는지의 **정보 건축**이에요. 관계는 포함이에요. 프롬프트 엔지니어링은 컨텍스트 엔지니어링의 부분 집합이에요.

| 항목 | 프롬프트 엔지니어링 | 컨텍스트 엔지니어링 |
|---|---|---|
| 대상 | 한 턴의 입력 문구 | 윈도우 전체의 토큰 구성 |
| 시점 | 대화 시작 전 1회 | 매 스텝마다 동적 갱신 |
| 범위 | 단어 선택, 예시, 역할 | 시스템 프롬프트 + 도구 + 메모리 + 이력 + 도구 출력 |
| 비유 | 벽 페인트칠 | 건물 골조 |

건물을 짓는 것에 비유하면 이해가 빨라요. 프롬프트를 쓰는 것은 벽에 페인트칠을 하는 거예요. 컨텍스트를 설계하는 것은 건물의 골조를 세우는 거예요. 페인트칠도 중요하지만, 골조가 부실하면 건물이 무너져요.

## 4. 4축 프레임워크 — Write, Select, Compress, Isolate

Lance Martin이 2025년 6월에 제시한 4축이 표준 프레임워크가 됐어요. LLM을 운영체제에, 윈도우를 RAM에 비유한 분류예요.

### Write — 윈도우 밖에 저장해요

컨텍스트 윈도우는 유한하므로 필요 없는 것은 밖으로 빼야 해요. CLAUDE.md가 대표적 구현이에요. 프로젝트 루트에 빌드 명령어·코드 스타일·디렉토리 구조를 적어두면, <Term id="T-HARNESS" />가 매 세션 시작 시 자동으로 로드해요.

### Select — 필요한 조각만 꺼내와요

프로젝트의 모든 파일을 읽는 대신, 특정 함수만 추출해서 100줄만 로드하는 거예요. 도서관에서 모든 책을 책상 위에 올려놓는 대신, 서가 목록만 훑어보고 필요한 책만 꺼내 오는 것과 같아요. <Term id="T-RAG" />도 이 축에 속해요.

### Compress — 같은 의미를 더 적은 토큰으로

컨텍스트가 임계값을 넘으면 이전 대화를 자동으로 요약해요. 1,200줄짜리 파일 내용이 한 줄 요약으로 바뀌면 60~80% 토큰 절감이 가능하고, 품질 손실은 5% 미만이에요.

압축에는 **우선순위**가 있어요. 도구 출력이 80%+를 차지하므로 가장 먼저 압축해요. 두 번째는 오래된 턴, 세 번째는 검색된 문서예요. **시스템 프롬프트는 절대 압축하지 않아요.** 압축하면 모델의 기본 행동이 바뀌기 때문이에요.

### Isolate — 컨텍스트를 나눠요

하나의 거대한 컨텍스트 대신 여러 개의 격리된 컨텍스트로 나누는 거예요. 메인 에이전트가 전체를 관리하고, <Term id="T-SUBAGENT" />가 각자 독립된 컨텍스트에서 탐색한 뒤 응축 요약만 돌려보내는 구조예요.

여기서 중요한 논쟁이 있어요. Cognition은 멀티에이전트를 쓰지 말라고 권고하고, Anthropic은 병렬 서브에이전트로 리서치 성능이 90% 향상됐다고 보고해요. 이 둘은 모순이 아니에요. Cognition이 말하는 것은 **컨텍스트를 공유하려는** 멀티에이전트의 실패이고, Anthropic이 말하는 것은 **컨텍스트를 격리하는** 서브에이전트의 성공이에요. 분리해야 하는 것은 역할이 아니라 **컨텍스트**인 거예요.

### 실전 — 100개 파일 리팩토링

| 축 | 적용 | 효과 |
|---|---|---|
| Write | CLAUDE.md에 마이그레이션 규칙 저장 | 매 세션 자동 로드. 100번 반복 설명 불필요 |
| Select | 파일을 3~5개씩 나눠 로드 | 필요한 것만 로드해 윈도우 폭발 방지 |
| Compress | 수정 완료 후 도구 출력을 한 줄 요약으로 대체 | 60~80% 절감 |
| Isolate | 메인이 계획, 서브에이전트가 폴더별 독립 작업 | 각자 깨끗한 컨텍스트에서 작업 후 결과만 반환 |

### 70~80%의 법칙

컨텍스트 윈도우를 얼마나 채워야 할까요? 답은 **70~80%까지**예요. 그 이상 채우면 성능이 무너지기 시작해요. 자동 압축은 비상 브레이크이지 정상 운전이 아니에요.

안정적인 요소(시스템 프롬프트, CLAUDE.md)를 앞에, 변하는 요소(대화 기록, 도구 출력)를 뒤에 배치하면 <Term id="T-LONGCTX" /> 환경에서 프리픽스 캐싱 효율이 올라가요.
