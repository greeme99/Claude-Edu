## 1. Product Overhang — 능력은 있는데 제품이 없었다

### 세계에서 가장 똑똑한 모델이 가장 무능해지는 순간

채팅 인터페이스에서 "이 프로젝트의 auth 모듈을 리팩토링해줘"라고 말해보세요. 돌아오는 답은 "프로젝트의 코드를 보여주시면 도와드리겠습니다"예요. 파일을 읽을 수 없고, 코드를 실행할 수 없고, 결과를 검증할 수 없습니다.

같은 말을 에이전트 도구에서 해보세요. 프로젝트 구조를 탐색하고, 관련 파일을 읽고, 코드를 수정하고, 테스트를 실행하고, 실패하면 수정하고 다시 테스트합니다. **같은 모델이에요.** 달라진 것은 모델을 감싸는 소프트웨어, 즉 <Term id="T-HARNESS" />입니다.

세계 최고의 외과 의사에게 수술실도, 메스도, 모니터도 주지 않고 빈 방에 세워놓으면 어떻게 될까요? 아무리 뛰어난 의사라도 할 수 있는 것이 없어요. 하네스는 이 의사에게 수술실과 도구를 갖춰주는 것과 같습니다.

### 같은 모델, 다른 제품

Boris Cherny는 이 현상을 **Product Overhang**이라 불렀어요. 모델의 능력은 이미 충분한데, 그 능력을 제품으로 만드는 소프트웨어가 없었다는 뜻입니다.

| 항목 | 채팅 | 에이전트 |
|---|---|---|
| 모델 | 동일 | 동일 |
| 파일 접근 | 불가능 (사용자가 복사) | 자동 탐색·읽기·수정 |
| 코드 실행 | 불가능 | 직접 실행 |
| 검증 | 불가능 (사용자가 확인) | 테스트 자동 실행, 실패 시 재수정 |
| 루프 | 사람이 수동 반복 | 소프트웨어가 자동 반복 |
| 작업 시간 | 30분 (대화 10회) | 3분 (자동 루프) |

**모델이 갑자기 똑똑해진 것이 아니에요.** 모델은 그대로인데 접근할 수 있는 것이 달라진 겁니다. 눈가리개를 벗겨준 것과 같아요.

## 2. 하네스의 두 가지 역할

하네스란 **LLM을 보이지 않는 프롬프트와 호출 가능한 도구로 확장하는 소프트웨어**입니다. 이 정의에 두 가지 역할이 다 담겨 있어요.

### 역할 1 — 보이지 않는 프롬프트를 관리해요

사용자가 "이 파일 고쳐줘"라고 한 줄을 치면, 실제로 모델에게 전달되는 것은 그 한 마디가 아니에요. <Term id="T-SYSP" /> 약 5,000 토큰, <Term id="T-CLAUDEMD" /> 내용, 도구 정의 목록, 이전 대화 기록이 앞에 붙습니다. **사용자는 한 줄을 썼지만 모델은 수만 토큰을 받은 셈이에요.**

병원에 가서 의사에게 "배가 아파요"라고 한 마디를 하죠. 그런데 의사가 보는 것은 그 말만이 아니에요. 차트에는 과거 진료 기록, 알레르기 정보, 복용 중인 약, 최근 검사 결과가 다 적혀 있습니다. 환자는 한 마디를 했지만, 의사는 수십 페이지의 맥락 위에서 그 한 마디를 해석해요.

보이지 않는 부분에 포함되는 것:

- **시스템 프롬프트** — 모델의 행동 규칙, 응답 형식, 제약 조건
- **CLAUDE.md** — 프로젝트별 설정 (빌드 명령어, 코드 스타일, 디렉토리 구조)
- **도구 정의** — 사용 가능한 도구 목록과 각 도구의 사용법
- **대화 이력** — 이전 턴의 전체 내용. LLM은 무상태이므로 매번 재전송

### 역할 2 — 호출 가능한 도구를 제공해요

모델이 외부 세계와 상호작용하는 통로예요. 모델이 "auth.ts 파일을 읽어야겠다"고 판단하면 Read 도구를 호출하고, 하네스가 실제로 파일을 읽어서 결과를 컨텍스트에 넣습니다.

의사가 "혈액 검사를 해주세요"라고 간호사에게 지시하는 것과 같아요. 의사가 직접 피를 뽑는 것이 아니라, 지시를 내리면 간호사(하네스)가 실행하고 결과를 가져다줍니다.

핵심은 **LLM이 무상태(stateless)** 라는 점이에요. LLM은 매번 실행될 때마다 같은 백지에서 시작합니다. 대화가 이어지는 것처럼 보이지만 실제로는 하네스가 매번 전체 대화 이력을 다시 전송해요. 이 재구성을 자동으로 처리하는 것이 하네스의 일입니다.

<Callout type="key">
하네스의 두 역할 — (1) **보이지 않는 프롬프트 관리** = 사용자의 한 마디에 풍부한 맥락 붙이기, (2) **호출 가능한 도구 제공** = 모델이 외부 세계와 상호작용하게 하기. 이 둘이 합쳐지면 채팅봇이 에이전트가 됩니다.
</Callout>

## 3. CLAUDE.md — 에이전트의 두뇌를 설계하는 방법

보이지 않는 프롬프트 중 가장 중요한 것이 CLAUDE.md예요. 프로젝트 루트에 놓는 파일 하나가 에이전트의 행동 전체를 바꿉니다.

### 나쁜 CLAUDE.md vs 좋은 CLAUDE.md

새로 온 인턴에게 업무를 맡긴다고 생각해보세요.

**나쁜 지시** — "일 잘 해주세요. 꼼꼼하게요."
아무 정보도 주지 않아요. "좋은 일"이 뭔지, "꼼꼼하다"는 게 어떤 기준인지 인턴은 알 수 없습니다.

**좋은 지시** — "월요일 아침 9시까지 주간 보고서를 작성해주세요. 형식은 공유 폴더의 템플릿을 따르고, 숫자는 ERP에서 뽑아주세요. 완성되면 팀장님 메일로 보내기 전에 저한테 먼저 확인받아주세요."
구체적이고, 실행 가능하고, 검증 기준이 있어요.

| 나쁜 CLAUDE.md | 좋은 CLAUDE.md |
|---|---|
| 코드를 잘 짜주세요. 테스트도 꼼꼼히 하고. 사용자 경험을 중시합니다. | 빌드/테스트: `npm run build`, `npm test`<br />코드 스타일: TypeScript strict, 함수형 우선, `any` 금지<br />커밋 규칙: conventional commits<br />구조: `src/api/`(라우트), `src/domain/`(로직), `src/infra/`(DB) |

### 네 가지 구성 요소

| 구성 요소 | 역할 | 예시 |
|---|---|---|
| 빌드/테스트 명령어 | 코드를 실행하고 검증하는 방법 | `npm run build`, `pytest -v` |
| 코드 스타일 규칙 | 일관된 코드를 작성하는 기준 | TypeScript strict, `any` 금지 |
| 디렉토리 구조 | 어떤 파일이 어디 있는지의 지도 | `src/api/`, `src/domain/` |
| 커밋 규칙 | 변경사항을 기록하는 형식 | conventional commits, 커밋 전 테스트 통과 |

에이전트가 첫 턴에서 "이 프로젝트는 어떻게 돌아가는가"를 즉시 파악할 수 있어야 해요. CLAUDE.md가 잘 쓰여 있으면 **프로젝트 탐색에 쓰는 턴 수가 줄어들고, 그만큼 실제 작업에 더 많은 컨텍스트 예산을 쓸 수 있습니다.**

핵심은 이거예요. **CLAUDE.md는 사람이 읽는 문서가 아니라 에이전트가 실행하는 지침입니다.** README는 사람을 위한 것이고, CLAUDE.md는 AI를 위한 거예요.

### 비개발자를 위한 이해

개발을 하지 않는 분도 이 원리를 이해할 수 있어요. CLAUDE.md는 결국 **새로 온 사람에게 주는 업무 매뉴얼**입니다.

- **어떻게 확인하나요?** — 결과물 제출 전 거쳐야 할 절차 (빌드/테스트)
- **어떤 규칙을 따르나요?** — 보고서 형식, 언어 스타일, 브랜드 가이드라인 (코드 스타일)
- **뭐가 어디에 있나요?** — 공유 폴더 구조, 담당자 연락처 (디렉토리 구조)
- **완료 보고는 어떻게 하나요?** — 일일 보고 양식, 승인 절차 (커밋 규칙)

이 넷을 미리 정리해두면 새 직원이 첫날부터 일할 수 있어요. 정리하지 않으면 첫 주를 질문하는 데 다 보냅니다. AI 에이전트도 정확히 같아요.

## 4. 에이전트 루프 — 수집, 행동, 검증, 반복

하네스의 심장은 루프예요. 원형은 ReAct 패턴 — 추론 흔적과 행동을 교차시키는 것입니다. 모델이 무엇을 해야 하는지 추론하고, 행동하고, 결과를 관찰하고, 다시 추론해요.

**Gather → Act → Verify → Repeat.** 이것이 <Term id="T-LOOP" />입니다.

### 의사의 진료 과정으로 이해하기

| 단계 | 에이전트 | 의사 | 도구 |
|---|---|---|---|
| Gather (수집) | 파일 탐색, 코드 검색 | 문진, 검사 결과 확인 | grep, Read, Glob |
| Think (추론) | 원인 분석 | 진단 | 모델 내부 |
| Act (행동) | 코드 수정 | 처방, 시술 | Edit, Bash |
| Verify (검증) | 테스트 실행 | 경과 관찰 | Bash (test) |
| Repeat (반복) | 실패 시 다시 수집부터 | 호전 없으면 재검사 | 루프 계속 |

의사가 한 번의 진찰로 모든 병을 알아내지 못하는 것처럼, 에이전트도 한 번에 완벽한 답을 내지 못해요. **반복하면서 점점 정답에 가까워지는 것**이 핵심입니다.

### 실전 — 로그인 버그 수정

| 단계 | 행동 | 내용 |
|---|---|---|
| Gather | grep, Read | `src/`에서 login 검색. 관련 파일 5개 발견 |
| Think | 추론 | 42번 줄에서 토큰 만료 체크가 빠짐 |
| Act | Edit | 42번 줄 수정 |
| Verify | Bash | `npm test` 실행. 1건 실패 |
| Think | 추론 | 타임존 문제 파악. UTC 변환 필요 |
| Act | Edit | 재수정 |
| Verify | Bash | 전체 테스트 통과 |

이 전체 과정에서 사람이 개입한 것은 처음 "로그인 버그 고쳐줘" 한 마디뿐이에요.

여기서 가장 중요한 단계가 뭘까요? **검증(Verify)** 입니다. 검증이 빠지면 에이전트는 "고쳤다"고 보고하면서 실제로는 망가뜨린 상태가 돼요. 의사가 약을 처방하고 경과를 확인하지 않는 것과 같습니다.

## 5. ACI — 도구 설계가 프롬프트보다 중요해요

### 절대경로 하나가 성패를 갈랐어요

Anthropic 연구진이 SWE-bench 코딩 벤치마크를 풀면서 발견한 것이 있어요. **프롬프트보다 도구 최적화에 더 많은 시간을 썼다**고 합니다. 구체적으로, 파일 편집 도구에서 **상대 경로를 절대 경로로 바꾸는 것만으로 도구 사용 오류가 완전히 사라졌어요.**

누군가에게 "3층 회의실로 가세요"라고 말하면, 이 사람이 지금 어느 건물에 있느냐에 따라 전혀 다른 곳에 갈 수 있어요. 하지만 "서울시 강남구 OO빌딩 3층 301호"라고 말하면 어디에 있든 정확히 도착합니다.

### ACI 설계의 세 가지 원칙

Anthropic은 이 원칙을 <Term id="T-ACI" /> 디자인이라 불러요. 인간-컴퓨터 인터페이스(HCI)에 들이는 노력만큼을 에이전트-컴퓨터 인터페이스에도 들여야 한다는 겁니다.

| 원칙 | 뜻 | 실천 방법 |
|---|---|---|
| 모델의 입장에서 생각할 것 | 모델이 도구를 처음 보는 주니어 개발자라고 상상해요. 암묵적 규칙은 없어요 | 파라미터 이름, 반환값 형식, 에러 시 행동을 명시 |
| 주니어에게 설명하듯 문서를 쓸 것 | 모호한 설명은 모호한 결과를 낳아요 | 도구 설명은 길어도 괜찮아요. 수백 줄이 될 수도 |
| 실수가 어렵도록 설계할 것 | 잘못 쓸 수 있는 설계는 반드시 잘못 쓰여요 | 상대 경로 대신 절대 경로 강제. 위험한 기본값 제거 |

도구 정의 자체가 컨텍스트 예산을 잡아먹는다는 점도 중요해요. 도구가 많을수록 컨텍스트가 줄어듭니다. 그래서 **도구는 적게, 하지만 정확하게** 설계하는 것이 원칙이에요.

<Callout type="key">
나쁜 프롬프트보다 **나쁜 도구 설명이 더 치명적**입니다. 프롬프트는 한 번 읽히지만, 도구 정의는 매 턴마다 컨텍스트에 포함되기 때문이에요.
</Callout>

## 6. 검증 3단계 — 에이전트를 믿되 확인해요

학생이 시험을 봤다고 생각해보세요.

| 단계 | 방법 | 장점 | 한계 |
|---|---|---|---|
| 1단계 | 규칙 기반 (lint, type check, test) — OMR 기계 채점 | 가장 빠르고 저렴. 자동화 용이 | 정해진 규칙만 검사 가능 |
| 2단계 | 시각적 피드백 (브라우저 스크린샷) — 선생님이 직접 보기 | 사람이 보는 것과 같은 확인 | 설정 비용이 있음 |
| 3단계 | LLM-as-Judge (다른 AI가 판정) — 전문가에게 묻기 | 가장 유연. 복잡한 판단 가능 | 가장 비싸고 판정 자체가 틀릴 수 있음 |

실전에서는 순서대로 적용해요. **1단계로 거를 수 있는 것은 1단계에서 거르고, 안 되는 것만 상위 단계로 올립니다.** 이렇게 하면 비용과 정확성의 균형을 맞출 수 있어요.

장기 작업에서는 2단계의 가치가 특히 커요. 브라우저 자동화로 실제 화면을 캡처해서 모델에게 "이게 맞는 결과인가"를 판단시키는 방식입니다. 비용이 들지만 인간이 보는 것과 가장 가까운 검증이에요.

## 7. 서브에이전트 — 컨텍스트를 분리하는 기술

하나의 에이전트가 모든 것을 하면 컨텍스트가 빠르게 소진돼요. 책상 위에 서류를 쌓아가면서 일한다고 생각해보세요. 처음엔 5장으로 시작했는데 50장이 됐어요. 책상이 좁아서 아래쪽 서류는 더 이상 보이지 않습니다.

해결책은 간단해요. **새 책상을 하나 더 놓고, 특정 업무는 그 책상에서 따로 처리하는 거예요.** 끝나면 결과만 가져오면 됩니다.

<Term id="T-SUBAGENT" />가 이 해결책의 소프트웨어 버전이에요. 메인 에이전트가 작업을 격리된 컨텍스트 창에서 실행되는 서브에이전트에게 위임합니다. 완료되면 **결과 요약만** 메인에게 돌려줘요.

| 서브에이전트가 유효한 경우 | 불필요한 경우 |
|---|---|
| 독립적인 파일이나 모듈 단위 작업 | 파일 간 의존성이 높아 전체 맥락이 필요한 작업 |
| 탐색적 작업 (여러 디렉토리에서 정보 수집) | 한 파일 안에서의 단순 수정 |
| 병렬 처리가 가능한 반복 작업 | 사용자와의 대화 맥락이 중요한 작업 |

흥미로운 역설이 하나 있어요. 메인 에이전트가 3시간 동안 작업하면서 컨텍스트가 누적되면, **새 작업을 깨끗한 컨텍스트에서 시작하는 서브에이전트가 오히려 더 정확합니다.** 오래된 컨텍스트에 묻혀 있는 메인보다 방금 시작한 서브에이전트가 단일 작업에서는 더 나은 결과를 내는 역설이에요.

이 원리는 <LessonLink id="TH-03" />의 Isolate 축과 정확히 같습니다.

## 8. 반패턴 3가지 — 이렇게 하면 망해요

### 반패턴 1 — 워크플로우를 에이전트라고 부르기

입력을 받아 요약하고, 번역하고, 포맷팅하는 세 단계가 if-else로 고정돼 있다면 이것은 에이전트가 아니라 <Term id="T-WORKFLOW" />예요.

**워크플로우는 경로가 코드에 박혀 있고, <Term id="T-AGENT">에이전트</Term>는 경로가 모델의 추론에 의해 런타임에 결정됩니다.**

워크플로우는 자판기예요. 버튼을 누르면 정해진 음료가 나와요. 에이전트는 바리스타입니다. 손님의 취향을 물어보고, 재료를 확인하고, 상황에 맞게 만들어요. **자판기가 나쁜 것은 아니에요.** 문제는 자판기를 바리스타라고 부르면서 바리스타 수준의 유연성을 기대하는 겁니다.

### 반패턴 2 — 비즈니스 로직을 하네스에 직접 넣기

"Python 파일이면 Black, TypeScript 파일이면 Prettier"라는 분기를 하네스 코드에 직접 넣으면, 새 언어가 추가될 때마다 하네스를 수정해야 해요.

이런 규칙은 CLAUDE.md나 설정 파일에 넣어야 합니다. **하네스는 인프라여야 하고, 비즈니스 로직은 설정에 있어야 해요.**

### 반패턴 3 — 에이전트가 테스트를 수정하게 허용하기

이것이 가장 치명적입니다. "AI가 테스트를 수정해서 통과시켰습니다"라고 하면 **아무것도 검증되지 않은 거예요.**

시험에서 답이 틀렸는데, 답안지를 고치는 대신 채점 기준을 고쳐서 맞다고 표시하는 겁니다. 점수는 올라가지만 실력은 변하지 않았어요. 더 나쁜 것은, 이후로는 틀린 답도 다 맞다고 나오게 되니까 **실력이 나빠지고 있는지조차 알 수 없게 된다**는 점입니다.

<Callout type="warn">
에이전트가 테스트를 지우거나 수정하게 허용하는 것은 용납할 수 없습니다. 검증 루프의 기반 자체가 사라지기 때문이에요.
</Callout>

## 9. 설계 철학

좋은 하네스에는 하나의 설계 철학이 있어요. **비즈니스 로직을 최소화하고, 모델이 대부분의 일을 한다. 새 모델이 나올 때마다 코드를 지운다.**

의미는 명확해요. 좋은 하네스는 모델을 바꿔도 제품이 유지됩니다. 나쁜 하네스는 모델을 바꾸면 전체를 다시 써야 해요. **하네스는 인프라여야 하고, 특정 모델에 종속된 로직이 들어가면 안 됩니다.**

<Callout type="key">
1. **Product Overhang** — 모델 능력은 이미 충분한데 그것을 꺼내 쓸 소프트웨어가 없었어요
2. **하네스의 두 역할** — 보이지 않는 프롬프트 관리 + 호출 가능한 도구 제공
3. **CLAUDE.md** — 에이전트의 업무 매뉴얼. 빌드/테스트, 코드 스타일, 디렉토리 구조, 커밋 규칙
4. **에이전트 루프** — Gather · Act · Verify · Repeat. **검증이 빠지면 치명적**
5. **ACI 설계** — 도구를 처음 보는 사람처럼 명확하게. 프롬프트보다 도구 설명이 중요
6. **서브에이전트** — 컨텍스트 소진 문제를 별도 창으로 분리해 해결
7. **반패턴** — 워크플로우를 에이전트라 부르기, 하네스에 비즈니스 로직 넣기, 테스트 수정 허용
</Callout>

같은 버그 수정에 채팅에서는 30분이 걸리고 에이전트에서는 3분이 걸리는 이유는 모델의 추론 속도가 빨라진 것이 아니에요. **사람이 병목이던 구간이 자동화된 것**입니다.
