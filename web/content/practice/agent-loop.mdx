## 오늘 만들 결과물

Claude에게 **멀티파일 리팩토링**이라는 대규모 작업을 시키고, Claude가 분석 → 수정 → 테스트 → 자동 수정의 루프를 돌면서 작업을 완료하는 과정을 직접 관찰하게 돼요.

<Callout type="quote">
<LessonLink id="TH-04" />에서 <Term id="T-LOOP" />를 배웠어요. Claude Code는 이 루프를 자동으로 수행하는 <Term id="T-AGENT" />예요.

작은 작업에서는 루프가 한두 번이면 끝나요. 하지만 큰 작업에서는 수십 번 반복돼요. 루프를 세 단계로 표현하면 **Gather → Act → Verify** 예요.

- **Gather**: 정보 수집 (파일 읽기, 구조 분석)
- **Act**: 행동 수행 (코드 수정, 파일 생성)
- **Verify**: 결과 검증 (테스트 실행, 빌드 확인)
</Callout>

## 준비물

- `practice-todo-app` 프로젝트 (이전 실습에서 사용)
- Claude Code
- Python 3.11+ 및 pytest

## 1. 프로젝트 분석 요청 (Gather)

<Step n={1} title="Claude에게 프로젝트 전체를 분석시켜요">

큰 작업을 시키기 전에 **전체 그림**을 파악하는 단계가 필요해요. 먼저 프로젝트를 실습에 적합하게 만듭니다.

```
> 이 프로젝트를 간단한 할 일 관리 CLI 앱으로 만들어줘.
> src/main.py에 CLI, src/models.py에 Todo 모델,
> src/utils.py에 유틸리티 함수를 작성하고,
> tests/test_main.py에 기본 테스트도 작성해줘.
> 일부러 개선할 여지를 남겨줘 (타입 힌트 누락, 에러 처리 부족 등).
```

기본 코드가 생성되면 전체 분석을 요청하세요.

```
> 이 프로젝트 전체를 분석해줘.
> 각 파일의 역할, 파일 간 의존 관계, 잠재적 문제를 정리해줘.
```

Claude는 아래 순서로 움직여요.

| 순서 | 도구 | 행동 |
|---|---|---|
| 1 | Glob/Bash | 프로젝트의 파일 목록을 조회 |
| 2 | Read | 각 파일의 내용을 읽기 |
| 3 | Grep | import 문을 검색해서 의존 관계 파악 |
| 4 | — | 수집한 정보를 종합해서 분석 결과 정리 |

</Step>

<Callout type="key">
큰 작업을 시키기 전에 **"먼저 전체를 분석해줘"** 라고 요청하는 것이 중요해요. 분석 없이 바로 수정을 시키면 Claude가 전체 맥락을 놓치고 부분적으로만 수정할 수 있거든요.
</Callout>

<TryIt>

Claude의 분석 결과를 검토해보세요.

1. Claude가 찾아낸 문제 목록이 정확한가요?
2. 의존 관계 분석이 맞나요? (어떤 파일이 어떤 파일을 import 하는지)
3. 놓친 문제가 있나요?

빠진 부분이 있다면 "에러 처리 부분도 점검해줘"처럼 구체적으로 요청하면 더 깊이 분석해요.

</TryIt>

## 2. 멀티파일 수정 지시 (Act)

<Step n={2} title="여러 파일을 동시에 수정하는 큰 작업을 시켜요">

```
> 분석 결과를 바탕으로 아래 개선을 수행해줘:
> 1. 모든 함수에 타입 힌트 추가
> 2. 모든 함수에 Google 스타일 docstring 추가 (한글)
> 3. 에러 처리 보강 (구체적 예외 타입 사용)
> 4. 테스트 커버리지 확대 (각 함수당 최소 1개 테스트)
> 5. 수정 후 모든 테스트가 통과하는지 확인
```

이 요청은 단순하지 않아요. Claude는 여러 파일을 돌아다니면서 수정해야 하고, 파일 간 의존성도 고려해야 해요. `models.py`의 클래스를 수정하면 `main.py`에서 그 클래스를 사용하는 부분도 맞춰서 바꿔야 하죠.

| 순서 | 행동 |
|---|---|
| 1 | 의존성 순서를 파악 (models → utils → main) |
| 2 | 가장 기초가 되는 파일부터 수정 (models.py) |
| 3 | 상위 파일을 수정하면서 하위 변경에 맞춰 조정 |
| 4 | 테스트 파일을 수정 |
| 5 | 테스트를 실행해서 확인 |

멀티파일 수정의 핵심은 **순서**예요. 이 순서가 뒤바뀌면 중간에 에러가 발생할 수 있어요.

</Step>

### 대규모 작업 요청의 좋은 패턴

| 나쁜 요청 | 좋은 요청 |
|---|---|
| "코드 좀 개선해줘" | "모든 함수에 타입 힌트를 추가하고 테스트를 확인해줘" |
| "전체적으로 고쳐줘" | "1. 타입 힌트 2. docstring 3. 에러 처리 순으로 개선해줘" |
| "완벽하게 만들어줘" | "CLAUDE.md 규칙을 기준으로 위반 사항을 수정해줘" |

좋은 요청의 특징은 **구체적이고, 번호가 있고, 완료 조건이 명확한 것**이에요.

## 3. 테스트 실행과 자동 수정 관찰 (Verify)

<Step n={3} title="테스트 실패 시 Claude가 자동으로 수정하는 과정을 관찰해요">

멀티파일 수정 후 테스트를 실행하면 높은 확률로 일부가 실패해요. 이때 Claude가 어떻게 반응하는지가 **에이전트의 진가가 드러나는 순간**이에요.

<LessonLink id="PR-07" />에서 CLAUDE.md에 테스트 명령어를 적어두었기 때문에 Claude는 `pytest tests/ -v`를 자동으로 실행할 거예요.

| 루프 | 단계 | 행동 |
|---|---|---|
| 1회차 | Verify | pytest 실행 → 3개 중 1개 실패 |
| 1회차 | Gather | 실패한 테스트의 에러 메시지 분석 |
| 1회차 | Act | 원인 파악 후 코드 수정 |
| 2회차 | Verify | pytest 재실행 → 전부 통과 |

</Step>

<TryIt>

자동 수정 루프를 더 깊이 관찰해보세요.

1. Claude가 테스트를 몇 번 반복 실행하는지 세어보세요
2. 각 루프에서 어떤 도구를 사용하는지 기록해보세요
3. Claude가 "원인"을 어떻게 추론하는지 관찰하세요 (에러 메시지의 어떤 부분을 읽나요?)

3번 이상 반복해도 통과하지 못한다면 **추가 힌트가 필요하다는 신호**예요. "에러가 파라미터 타입 때문인 것 같아"처럼 방향을 잡아주세요.

</TryIt>

### 테스트를 일부러 실패시켜보기

루프를 더 명확하게 관찰하기 위해 일부러 실패시켜볼게요.

```
> tests/test_main.py에 일부러 실패하는 테스트를 2개 추가해줘.
> 하나는 존재하지 않는 함수를 호출하고,
> 다른 하나는 잘못된 반환값을 기대하는 테스트야.
> 그런 다음 모든 테스트가 통과하도록 수정해줘.
```

Claude가 처리하는 과정을 지켜보세요.

1. 먼저 실패하는 테스트를 추가해요
2. pytest를 실행해서 실패를 확인해요
3. 실패 원인을 분석해요 (함수가 없다, 반환값이 다르다)
4. 원인에 맞게 코드를 수정해요 (함수 추가, 로직 수정)
5. 다시 pytest를 실행해요
6. 모두 통과하면 완료를 보고해요

<Callout type="key">
에이전트 루프의 핵심 가치는 **"실패를 자동으로 복구하는 능력"** 이에요. 사람이라면 에러를 보고 → 원인 분석 → 수정 → 재실행을 수동으로 해야 하지만, 에이전트는 이걸 자동으로 반복해요.
</Callout>

## 4. 세 단계를 분리해서 제어하기

**Gather (정보 수집)** — 파일 구조 파악(Glob, Bash), 파일 내용 읽기(Read), 패턴 검색(Grep), 의존성 분석, 기존 테스트 확인.
*여러분이 할 수 있는 것*: "먼저 전체를 분석해줘"라고 명시적으로 Gather를 요청하세요.

**Act (행동 수행)** — 코드 수정(Edit, Write), 파일 생성/삭제, 설정 변경.
*여러분이 할 수 있는 것*: 변경 범위와 우선순위를 명확히 지시하세요.

**Verify (결과 검증)** — 테스트 실행, 빌드 확인, 결과 보고.
*여러분이 할 수 있는 것*: CLAUDE.md에 검증 명령어를 적어두세요. Claude가 자동으로 사용해요.

| 단계 | Claude가 하는 일 | 여러분이 도울 수 있는 것 |
|---|---|---|
| Gather | 파일 읽기, 구조 분석 | CLAUDE.md에 프로젝트 구조 작성 |
| Act | 코드 수정, 파일 생성 | 명확한 요구사항과 우선순위 |
| Verify | 테스트, 빌드 확인 | CLAUDE.md에 테스트/빌드 명령어 |

<TryIt>

에이전트 루프를 의식적으로 분리해서 사용해보세요.

1. **Gather만**: "프로젝트 전체를 분석하고 개선 포인트를 정리해줘"
2. 분석 결과를 확인한 뒤, **Act만**: "분석 결과 중 1, 3, 5번을 수정해줘"
3. 수정 결과를 확인한 뒤, **Verify만**: "모든 테스트를 실행하고 결과를 알려줘"

이렇게 단계를 나누면 각 단계에서 Claude의 행동을 더 정밀하게 제어할 수 있어요.

</TryIt>

## 5. 에이전트 자율성 조절

| 수준 | 설명 | 적합한 상황 |
|---|---|---|
| **높은 자율성** | 분석부터 수정, 테스트까지 한번에 | 잘 정의된 반복 작업, 테스트가 충분한 프로젝트 |
| **중간 자율성** | 수정은 하되 매 단계 확인 | 새로운 기능 추가, 중요한 리팩토링 |
| **낮은 자율성** | 분석만 하고 수정은 승인 후 | 프로덕션 코드, 보안 관련 변경 |

<Callout type="warn">
에이전트의 자율성은 **테스트 커버리지에 비례해서** 높여야 해요. 테스트가 촘촘하면 Claude가 잘못 수정해도 테스트에서 잡히니까요. **테스트가 없는 코드에서는 자율성을 낮추세요.**

권한 확인 없이 실행하는 모드도 있지만, 일반적인 실습에서는 기본 모드로 충분해요. 파일 수정이나 명령어 실행 시 확인을 요청하는 것이 안전해요.
</Callout>

## 6. 핵심 용어

| 용어 | 설명 |
|---|---|
| **에이전트 루프** | 인식→계획→실행→관찰의 반복 사이클. Gather/Act/Verify로도 표현 |
| **Gather** | 행동 전 정보를 수집하는 단계. 파일 읽기, 구조 분석 등 |
| **Act** | 수집한 정보를 바탕으로 실제 변경을 수행하는 단계 |
| **Verify** | 변경 결과를 검증하는 단계. 테스트 실행, 빌드 확인 등 |
| **멀티파일 수정** | 여러 파일을 동시에 수정하는 대규모 작업 |
| **자동 수정 루프** | 테스트 실패 시 원인 분석→수정→재테스트를 자동 반복하는 과정 |

## 7. 트러블슈팅

<Troubleshoot q="Claude가 수정을 시작하지 않고 분석만 계속해요.">
분석이 끝났으면 "이제 수정을 시작해줘"라고 명시적으로 Act 단계로 전환을 요청하세요. Claude는 불확실하면 행동보다 분석을 선호하는 경향이 있어요.
</Troubleshoot>

<Troubleshoot q="테스트가 실패하는데 Claude가 자동으로 수정하지 않아요.">
"테스트가 실패하면 원인을 분석하고 자동으로 수정한 뒤 다시 테스트를 실행해줘"라고 명시적으로 지시하세요. 또는 CLAUDE.md에 "수정 후 반드시 테스트를 실행하고, 실패 시 수정을 반복한다"는 규칙을 추가하세요.
</Troubleshoot>

<Troubleshoot q="Claude가 자동 수정 루프에서 같은 실수를 반복해요.">
힌트를 주세요. "이전 수정이 같은 에러를 반복하고 있어. 다른 접근 방식을 시도해봐"라고 하면 전략을 바꿔요. 3회 이상 같은 에러면 사람이 방향을 잡아주는 것이 효율적이에요.
</Troubleshoot>

<Troubleshoot q="멀티파일 수정 중에 Claude가 엉뚱한 파일을 수정해요.">
수정 대상 파일을 명시적으로 지정하세요. "수정할 파일: src/main.py, src/models.py, tests/test_main.py. 다른 파일은 건드리지 마"라고 범위를 제한하세요.
</Troubleshoot>

<Callout type="key">
1. 큰 작업은 **Gather → Act → Verify** 세 단계로 구성돼요
2. 멀티파일 수정 시 Claude는 **의존성 순서**를 파악해서 기초 파일부터 수정해요
3. 테스트 실패 시 **자동으로 원인 분석 → 수정 → 재테스트** 루프를 돌아요
4. 자율성은 **테스트 커버리지에 비례**해서 조절해야 해요
5. CLAUDE.md에 빌드/테스트 명령어를 적어두면 Verify가 자동화돼요
</Callout>
