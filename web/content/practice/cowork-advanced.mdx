## 오늘 만들 결과물

<LessonLink id="PR-13" />에서 한 번 성공한 작업이 **매주 월요일 아침 혼자 실행되는 상태**가 돼요. 그 과정에서 스킬 하나, 커넥터 연결 하나, 스케줄 작업 하나를 만들게 됩니다.

<Callout type="quote">
Cowork의 커스터마이즈는 **3단계**로 올라가요.

| 단계 | 무엇 | Claude Code로 치면 |
|---|---|---|
| **1. 맥락과 도구** | 지침 + 커넥터 | `CLAUDE.md` + MCP 서버 |
| **2. 절차 포착** | 스킬 | `.claude/commands/*.md` |
| **3. 공유** | 플러그인 | Git 저장소에 커밋 |

<LessonLink id="TH-07" />에서 봤듯 **계층은 Claude Code와 동일**하고, 이름과 설치 방식만 사용자 언어로 바뀌어 있어요. 대부분의 사람은 커넥터와 지침으로 시작해서, 작업이 반복되면 스킬을 만들고, 팀원이 같은 세팅을 원할 때 플러그인으로 묶습니다.
</Callout>

## 준비물

- Claude 데스크톱 앱 (유료 플랜)
- <LessonLink id="PR-13" />에서 연결한 연습용 폴더
- 연결할 수 있는 업무 앱 하나 (Slack, Google Drive, Notion 등 — 없어도 진행 가능)

## 1. 커넥터 — 다른 앱 붙이기

<Step n={1} title="Customize 패널에서 커넥터를 켜요">

왼쪽 사이드바의 **Customize** 패널을 열면 연결 가능한 서비스 목록이 나와요. Slack, Google Drive, Notion, Jira, HubSpot, Microsoft 365 같은 것들이에요.

<LessonLink id="PR-08" />에서 `claude mcp add` 명령어로 MCP 서버를 붙였던 걸 기억하세요? **커넥터가 바로 그것**이에요. 같은 <Term id="T-MCP" /> 기반이고, 터미널 명령어가 **토글 하나**로 바뀐 것뿐입니다.

| | Claude Code | Cowork |
|---|---|---|
| 추가 | `claude mcp add ... -- npx ...` | Customize 패널에서 토글 |
| 목록 확인 | `claude mcp list` | Customize 패널 |
| 설정 저장 위치 | `~/.claude/settings.json` | 계정 설정 |

커넥터는 **읽기만이 아니라 쓰기도** 해요. 티켓을 업데이트하고, 답장 초안을 작성하고, 파일을 저장할 수 있어요.

</Step>

<Callout type="warn">
커넥터를 켤 때는 <LessonLink id="PR-08" />에서 배운 **최소 권한 원칙**이 그대로 적용돼요. 쓰기가 필요 없는 작업이라면 읽기 전용으로 두고, 쓰지 않는 커넥터는 꺼두세요. 도구가 너무 많으면 Claude가 적절한 도구를 고르는 데 오히려 방해가 됩니다.
</Callout>

<Step n={2} title="커넥터를 쓰는 작업을 한 번 돌려봐요">

커넥터를 하나 연결했다면, 로컬 폴더와 **함께** 쓰는 작업을 시켜보세요. 여기가 Cowork의 진짜 가치가 나오는 지점이에요.

```
이번 주 #프로젝트 채널에서 결정된 사항을 찾아서,
연결된 폴더의 회의록 파일들과 대조해줘.

- Slack에서 결정된 것 중 회의록에 반영이 안 된 항목을 찾아줘
- 반대로 회의록에는 있는데 Slack에서 후속 논의가 없는 항목도 찾아줘
- 결과를 표로 만들어 폴더에 주간_점검.md 로 저장해줘
- 출처(채널·날짜 또는 파일명)를 항목마다 붙여줘
```

커넥터가 없다면 로컬 폴더만으로 비슷한 작업을 해보세요.

```
연결된 폴더의 문서들을 읽고, 서로 모순되거나
중복되는 내용이 있는지 찾아서 표로 정리해줘.
근거가 되는 파일명과 위치를 항목마다 붙여줘.
```

</Step>

<Callout type="key">
**"출처를 붙여줘"** 를 항상 넣으세요. <Term id="T-HALL" />은 표면이 바뀌어도 사라지지 않아요. 출처가 붙어 있으면 검증이 1분이지만, 없으면 전부 다시 읽어야 해요. 출처 요구는 가장 싼 <Term id="T-GUARD" />입니다.
</Callout>

<Callout type="warn">
커넥터와 브라우저는 **외부 텍스트를 컨텍스트로 끌어들이는 통로**예요. 웹페이지나 문서에 숨겨둔 지시문이 에이전트의 행동을 조종하는 <Term id="T-PI" /> 위험이 실제로 존재합니다. 신뢰할 수 없는 출처의 내용을 읽은 세션에서 **쓰기 권한이 있는 작업을 자동 승인으로 돌리지 마세요.**
</Callout>

## 2. 스킬 — 한 번 한 일을 굳히기

<Step n={3} title="방금 한 작업을 스킬로 만들어요">

여기가 Cowork에서 가장 실용적인 기능이에요. 스킬을 만드는 가장 좋은 방법은 **먼저 작업을 한 번 제대로 해낸 다음, 그걸 포장해달라고 하는 것**입니다.

방금 작업이 만족스러웠다면 같은 세션에서 바로 요청하세요.

```
방금 우리가 한 작업을 스킬로 만들어줘.

포함할 것:
- 어떤 순서로 했는지
- 출처를 붙이고 추측하지 않는다는 규칙
- 결과를 표로 만들어 폴더에 저장한다는 형식
- 다음에는 대상 기간만 바꿔서 쓸 수 있게 해줘
```

Claude의 스킬 생성기가 **방금 실행한 절차·템플릿·자료 위치를 포착**해서 재사용 가능한 형태로 묶어줘요.

</Step>

<Callout type="key">
이것이 <LessonLink id="PR-09" />에서 `commit.md`를 손으로 작성했던 것과 같은 결과물인데, 접근이 반대예요.

- **Claude Code 방식**: 절차를 먼저 상상해서 마크다운으로 쓴다 → 실행해본다 → 고친다
- **Cowork 방식**: 일단 한 번 해낸다 → **"이걸 스킬로 만들어줘"** → 다듬는다

두 번째가 훨씬 쉬워요. 이미 성공한 절차를 포장하는 것이니까요. 스킬 본문은 여전히 마크다운이고, 좋은 스킬의 조건도 <LessonLink id="PR-09" />와 동일합니다 — **구체적인 절차, 명확한 규칙, 좋은 description.**
</Callout>

<Step n={4} title="만든 스킬을 호출해봐요">

스킬은 두 가지 방식으로 부를 수 있어요.

```
/주간점검
```

또는 자연어로요.

```
지난주 기준으로 주간 점검 한번 돌려줘
```

자연어 호출이 되는 이유는 <LessonLink id="PR-09" />에서 배운 **자동 매칭**이에요. Claude가 요청과 각 스킬의 description을 비교해서 고릅니다. **description이 구체적일수록 정확도가 올라가요.**

</Step>

<TryIt>

스킬의 품질을 확인하는 가장 확실한 방법은 **같은 스킬을 3번 돌려보는 것**이에요.

1. `/스킬이름`을 세 번 실행하세요 (대상만 조금씩 바꿔서)
2. 세 결과물의 **구조**가 같은가요? (항목, 순서, 형식)
3. 세 결과물의 **품질**이 비슷한가요?

들쭉날쭉하다면 절차가 모호한 거예요. "적절히 정리하세요" 같은 문장을 찾아서 "아래 5개 항목을 순서대로 점검하세요"로 바꾸세요. <LessonLink id="PR-12" />에서 본 **재현성** 기준이 그대로 적용됩니다.

</TryIt>

## 3. 지침 — 매번 말하지 않아도 되게

스킬이 **"이 작업은 이렇게 해"** 라면, 지침은 **"모든 작업에서 이건 지켜"** 예요. <LessonLink id="PR-13" />에서 전역 지침을 맛봤다면, 여기서는 세 층을 구분해둘게요.

| 층 | 위치 | 범위 | 쓰는 내용 |
|---|---|---|---|
| **전역 지침** | 설정 → Cowork → 전역 지침 (데스크톱) | 모든 세션 | 언어, 톤, 안전 원칙 |
| **프로젝트 지침** | 프로젝트 우측 패널 | 해당 프로젝트 | 그 업무의 배경·용어·기준 |
| **조직 지침** | 관리자 설정 | 조직 전체 | 규정, 금지사항, 승인 절차 |

<LessonLink id="PR-07" />의 CLAUDE.md 계층 구조와 **정확히 같은 발상**이에요. 개인 선호는 위로, 프로젝트별 규칙은 아래로.

<TryIt>

지침을 어느 층에 둘지 판단해보세요. 아래 항목을 전역/프로젝트/조직으로 나눠보세요.

1. "모든 답변은 한국어로"
2. "우리 회사는 '고객'이 아니라 '파트너사'라고 부른다"
3. "개인정보가 포함된 파일은 외부 커넥터로 내보내지 않는다"
4. "이 프로젝트의 보고서는 항상 A4 1장으로"
5. "큰 작업은 계획을 먼저 보여주고 승인을 받는다"

답을 정하는 기준은 하나예요. **"이 규칙이 깨지면 곤란한 범위가 어디까지인가?"**

</TryIt>

## 4. 스케줄 작업 — 혼자 돌게 만들기

<Step n={5} title="반복 작업을 자동 실행으로 바꿔요">

스킬이 안정적으로 돌아간다면 이제 **사람이 시작 버튼을 누르는 것조차** 없앨 수 있어요.

**Scheduled** 섹션에서 작업을 만드는 방법은 두 가지예요.

| 방법 | 설명 | 추천 |
|---|---|---|
| **Claude와 함께 만들기** | Claude가 질문하며 설정을 안내 | 처음이라면 이쪽 |
| **직접 설정** | 이름·프롬프트·승인 모드·주기를 직접 입력 | 익숙해진 뒤 |

주기는 **시간별 / 매일 / 매주 / 평일 / 수동(온디맨드)** 중에서 고를 수 있어요.

각 스케줄 작업은 **자기만의 Cowork 세션으로 원격 실행**돼요. 그래서 내 컴퓨터가 꺼져 있어도 돌아갑니다. 일반 Cowork 작업에서 쓰던 **커넥터·스킬·설치한 플러그인을 그대로** 쓸 수 있어요.

</Step>

<Callout type="warn">
**스케줄 작업은 내 컴퓨터의 폴더에 묶을 수 없어요.**

클라우드에서 실행되기 때문이에요(<LessonLink id="TH-07" /> 4절). 그래서 설계가 갈립니다.

- **로컬 파일이 필요한 작업** → 스케줄로 만들 수 없어요. 수동 실행하거나, 파일을 Google Drive 같은 커넥터 쪽으로 옮겨야 해요
- **커넥터·웹만 쓰는 작업** → 스케줄에 딱 맞아요

주간 점검 스킬을 스케줄로 올리려면, 회의록이 로컬 폴더가 아니라 **커넥터로 접근 가능한 곳**에 있어야 한다는 뜻이에요.
</Callout>

<Step n={6} title="스케줄 작업을 관리해요">

Scheduled 섹션에서 할 수 있는 것들이에요.

- 예정된 실행과 지난 실행 기록 확인
- 지시문이나 주기 수정
- 일시정지 / 재개 / 삭제
- **수동으로 지금 한 번 실행**

마지막 항목이 중요해요. 스케줄을 만들었다면 **주기를 기다리지 말고 수동 실행을 한 번 눌러서** 제대로 도는지 확인하세요.

</Step>

<TryIt>

스케줄 작업 하나를 만들고 검증하세요.

1. 주기를 **주 1회**로 설정하고 만들어요
2. 만들자마자 **수동 실행**을 눌러요
3. 결과물이 기대한 대로 나왔는지 확인해요
4. 실패했다면 지시문을 고치고 다시 수동 실행해요

**주기를 기다려서 실패를 발견하면 일주일을 버리는 거예요.** 수동 실행으로 먼저 검증하는 것이 스케줄 작업의 첫 번째 규칙입니다.

</TryIt>

<Callout type="key">
스케줄 작업의 승인 모드를 정할 때 <LessonLink id="PR-11" />의 원칙을 다시 떠올리세요. 스케줄 실행 시점에는 **아무도 화면을 보고 있지 않아요.** 수동 승인 모드로 만든 스케줄 작업은 승인 대기에서 멈춰 있게 됩니다. 그래서 스케줄 작업은 **되돌릴 수 있고 결과를 나중에 검증할 수 있는 일**로 한정하는 것이 안전해요 — 예를 들어 "보고서를 만들어 두기"는 되지만 "메일을 보내기"는 신중해야 합니다.
</Callout>

## 5. 브라우저 — 커넥터가 없는 곳

커넥터가 제공되지 않는 시스템은 어떻게 할까요? 사내 레거시 포털, 관공서 사이트 같은 곳이요. 답은 **브라우저**예요.

| | **내장 브라우저** | **Claude in Chrome** |
|---|---|---|
| 정체 | 데스크톱 앱 안의 Claude 전용 브라우저 | 내 실제 Chrome |
| 내 탭·북마크·비밀번호 | 보지 않음 | 내 세션을 그대로 사용 |
| 적합한 일 | 통째로 위임하는 조사·수집 | 이미 로그인해 열어둔 페이지 |
| 설치 | 불필요 | 확장 프로그램 필요 |

내장 브라우저는 Chrome·Edge·Firefox에서 로그인을 가져올 수 있지만, **은행·이메일·SSO 사이트는 기본적으로 제외**돼요.

<Callout type="key">
우선순위는 명확해요. **커넥터 > 브라우저.** 커넥터가 있으면 항상 그쪽이 더 빠르고 안전하고 안정적이에요. 브라우저는 **정식 통로가 없을 때의 비상구**입니다. 화면 구조가 바뀌면 깨지기 때문에 브라우저 기반 자동화는 스케줄로 올릴 때 특히 조심해야 해요.
</Callout>

<TryIt>

브라우저를 쓰는 작업을 하나 시켜보세요.

```
아래 세 사이트에서 [주제]에 대한 최근 자료를 찾아
핵심 내용과 링크를 표로 정리해줘. 출처 링크를 반드시 붙여줘.
결과는 폴더에 조사_[주제].md 로 저장해줘.
```

Claude가 브라우저를 열고 페이지를 읽는 과정을 관찰하세요. **커넥터로 할 수 있는 일이었는지** 판단해보는 것도 좋은 연습이에요.

</TryIt>

## 6. 플러그인 — 팀에 배포하기

<Step n={7} title="스킬과 커넥터를 하나로 묶어요">

혼자 쓰던 세팅을 팀원도 쓰게 하려면 **플러그인**으로 묶어요. 플러그인은 **커넥터와 스킬을 함께 담은 꾸러미**예요.

Anthropic이 영업·제품·법무·운영 같은 역할별 플러그인을 미리 제공하고, Customize 사이드바에서 둘러볼 수 있어요. 직접 만들 수도 있습니다.

```
지금까지 만든 스킬과 켜둔 커넥터를
팀에서 쓸 수 있는 플러그인으로 묶어줘.

- 플러그인 이름과 설명을 정해줘
- 포함할 스킬과 커넥터 목록을 보여주고 확인받아줘
- 팀원이 설치 후 처음 해봐야 할 작업을 안내에 넣어줘
```

</Step>

<Callout type="key">
<LessonLink id="PR-10" />에서 배운 원칙이 여기서도 유효해요. **하나의 스킬, 하나의 책임.** 플러그인은 그 스킬들을 묶는 포장지이지, 하나의 거대한 스킬을 만드는 도구가 아니에요. 5단계를 넘는 절차는 2~3개 스킬로 쪼개고 플러그인으로 묶는 편이 유지보수에 훨씬 유리합니다.
</Callout>

<Callout type="warn">
공유 전에 **스킬을 검증**하세요. 내 컴퓨터에서만 되는 경로, 나만 접근 권한이 있는 커넥터, 내 폴더 구조를 전제한 절차가 섞여 있으면 팀원 환경에서 깨져요. 팀원 한 명에게 먼저 설치시켜 **한 번 돌려보게 하는 것**이 배포 전 마지막 관문입니다.
</Callout>

## 7. 확장 순서 정리

<div className="stratum">

| 신호 | 다음 단계 |
|---|---|
| 매번 같은 배경 설명을 붙이고 있다 | → **지침**에 올린다 |
| 다른 앱의 데이터를 복붙해 오고 있다 | → **커넥터**를 켠다 |
| 같은 절차를 두 번 이상 반복했다 | → **스킬**로 만든다 |
| 스킬이 3번 연속 안정적으로 돌았다 | → **스케줄**로 올린다 |
| 팀원이 "그거 나도 쓰고 싶은데" 한다 | → **플러그인**으로 묶는다 |
| 커넥터가 없는 시스템을 써야 한다 | → **브라우저**를 쓴다 (최후 수단) |

</div>

<Callout type="q">
반대 방향의 질문도 해보세요. **"이건 자동화하면 안 되는 일 아닌가?"**

<LessonLink id="PR-12" />의 기준이 여기서도 그대로예요 — 최종 의사결정, 법적 책임이 있는 문서, 민감한 개인정보, **검증이 어려운 작업.** 스케줄 작업은 아무도 보고 있지 않을 때 실행되기 때문에 이 기준이 더 엄격하게 적용돼야 합니다.
</Callout>

## 8. 트러블슈팅

<Troubleshoot q="스케줄 작업이 매번 실패해요.">
로컬 폴더에 의존하고 있을 가능성이 가장 높아요. 스케줄 작업은 클라우드에서 실행되므로 내 컴퓨터의 폴더에 접근할 수 없어요. 작업 지시문에 로컬 경로가 들어 있는지 확인하고, 필요한 파일을 커넥터로 접근 가능한 곳으로 옮기거나 수동 실행 작업으로 바꾸세요.
</Troubleshoot>

<Troubleshoot q="스케줄 작업이 승인 대기에서 멈춰 있어요.">
수동 승인 모드로 만들었기 때문이에요. 실행 시점에 아무도 없으니 승인이 나지 않아요. 되돌릴 수 있는 작업이라면 자동 모드로 바꾸고, 승인이 꼭 필요한 작업이라면 스케줄이 아니라 수동 실행으로 두는 것이 맞아요.
</Troubleshoot>

<Troubleshoot q="스킬을 만들었는데 매번 결과가 달라요.">
절차에 모호한 문장이 있어요. "적절히", "잘", "필요하면" 같은 단어를 찾아서 구체적인 판단 기준으로 바꾸세요. 출력 형식도 엄격하게 지정하세요. <LessonLink id="PR-12" />의 재현성 점검(3번 실행)을 통과할 때까지 다듬는 것이 기준이에요.
</Troubleshoot>

<Troubleshoot q="자연어로 불러도 스킬이 매칭되지 않아요.">
description이 모호하거나 다른 스킬과 겹칠 수 있어요. 실제로 쓰는 표현을 description에 넣어보세요. 확실하게 부르고 싶으면 `/스킬이름`으로 직접 호출하는 게 답이에요.
</Troubleshoot>

<Troubleshoot q="커넥터를 켰는데 Claude가 안 써요.">
작업 지시에 그 앱을 쓰라고 명시해보세요("Slack의 #채널에서 찾아줘"). 그래도 안 되면 커넥터 연결 상태와 권한 범위를 확인하세요. 도구가 너무 많이 켜져 있으면 선택이 흐려지니 안 쓰는 커넥터는 꺼두는 것도 도움이 돼요.
</Troubleshoot>

<Troubleshoot q="팀원 환경에서 플러그인이 동작하지 않아요.">
내 환경에만 있는 전제가 스킬에 박혀 있을 거예요. 로컬 경로, 나만 가진 커넥터 권한, 내 폴더 구조 같은 것들이요. 스킬 본문을 읽으면서 "이 문장이 다른 사람 컴퓨터에서도 참인가?"를 한 줄씩 확인하세요.
</Troubleshoot>

<Troubleshoot q="사용량이 너무 빨리 소진돼요.">
Cowork는 자율 실행 때문에 일반 채팅보다 훨씬 많이 써요. 자동 승인 모드는 안전 점검을 추가로 돌아 더 씁니다. 스케줄 작업도 실행될 때마다 소비하니 주기를 필요 이상으로 촘촘하게 잡지 마세요. **Chat으로 충분한 일은 Chat에서** 하는 것이 가장 큰 절약이에요.
</Troubleshoot>

<Callout type="key">
1. 커스터마이즈는 **지침·커넥터 → 스킬 → 플러그인**의 3단계로 올라가요
2. **커넥터 = MCP**. 명령어가 토글로 바뀐 것뿐이고, 최소 권한 원칙은 그대로예요
3. 스킬은 **먼저 해낸 다음 "이걸 스킬로 만들어줘"** 가 가장 쉬운 길이에요
4. **스케줄 작업은 로컬 폴더에 묶을 수 없어요** — 클라우드에서 돌기 때문
5. 스케줄은 만들자마자 **수동 실행으로 검증**하세요
6. 커넥터가 우선, 브라우저는 정식 통로가 없을 때의 비상구
7. 공유 전에 **다른 사람 환경에서도 참인지** 한 줄씩 확인하세요
</Callout>
